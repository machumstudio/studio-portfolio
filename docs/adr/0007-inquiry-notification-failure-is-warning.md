# 0007. 문의 알림이 실패해도 저장은 유지하고 경고로 돌려준다
- 상태: 채택 (2026-10)

## 배경
문의 제출(`submitInquiry`)은 검증 → 저장 → 알림(15칸 이메일 또는 Slack) 순서다. 저장소와 알림은 서로 다른 외부 서비스라 한쪽만 실패할 수 있다.
스튜디오 입장에서 가장 나쁜 결과는 문의를 잃는 것이다. 알림을 놓쳐도 관리자 문의 목록(19칸)에는 남는다.

## 결정
- 저장이 성공하면 문의 제출은 성공이다. 알림 실패는 저장을 되돌리지 않고 결과의 `warnings`에 `NotificationFailed`로 담는다
- 저장이 실패하면 `StorageFailed` 에러이고 알림을 보내지 않는다 (없는 문의를 알리지 않는다)
- 포트(`InquiryRepository`, `Notifier`)는 장애를 Promise 거부로 알리고, 유스케이스가 받아서 `Result` 에러나 경고로 바꾼다. 어댑터는 SDK 예외를 그대로 던져도 되고, 도메인 에러 유니온은 어댑터 종류와 무관하게 유지된다
- 사용자 화면(13칸)은 경고가 있어도 "접수 완료"를 보여 주고, 서버는 경고를 로그로 남긴다

## 대안
- 알림 실패 시 전체 실패 + 저장 롤백: 사용자는 다시 보내야 하고, 알림 서비스 장애가 곧 문의 접수 장애가 된다
- 알림을 먼저 보내고 저장: 저장이 실패하면 목록에 없는 문의 알림이 간다
- 아웃박스 테이블 + 재시도 작업: 알림을 놓치지 않지만 스케줄러가 필요하다. 문의량(하루 수 건)에 비해 과하다. 필요해지면 `warnings`를 보고 재시도 큐로 옮길 수 있다
- 포트가 `Result`를 돌려주게 하기: 어댑터마다 예외를 잡는 코드가 반복된다. 장애 처리는 유스케이스 한 곳에 둔다

## 결과
- 알림 장애가 접수를 막지 않는다. 대신 알림을 놓친 문의는 관리자가 목록에서 확인해야 한다 (19칸 목록의 New 상태가 그 역할)
- 경고는 결과 타입에 드러나서 호출하는 쪽이 무시하기 어렵다
