# 0010. 저장된 행은 domain 복원 생성자로 되살리고, 인프라 매퍼는 칼럼 변환만 한다
- 상태: 채택 (2026-10)

## 배경
14칸에서 Supabase 리포지토리가 생기면서 DB 행을 도메인 객체로 되돌리는 코드가 필요해졌다.
작업은 이미 `createWork`가 "관리자 저장, 리포지토리에서 읽기, 시드 모두"를 맡는다. 문의는 `createInquiry`가 새 문의(항상 New)만 만들어서,
Read/Done 으로 저장된 문의를 되살릴 공식 경로가 없었다 (12칸 계약 테스트는 `{ ...createInquiry(...), status }`로 덮어썼다).
어디에서 검증하고 어디에서 모양을 바꿀지 정해야 한다.

## 결정
- 복원 규칙은 domain 에 둔다: `restoreInquiry(input, { id, receivedAt, status })`. 칸 검증은 `createInquiry`와 같고, 상태만 저장된 값을 쓴다. 작업은 지금처럼 `createWork`
- 인프라 매퍼(`infrastructure/<context>/supabase-*-mapper.ts`)는 표현만 바꾼다: snake_case 칼럼 → 도메인 입력, 문자열 시각 → `Date`, `status`/`status_changed_at` 두 칼럼 → `InquiryStatus`, `work_images.is_cover` → `coverSrc`. 규칙 판단은 하지 않고 domain 생성자를 부른다
- 복원이 실패한 행(규칙을 어긴 데이터)은 건너뛰지 않고 Promise 거부로 알린다. 포트 규약(저장소 장애는 거부)과 같고, 유스케이스가 `StorageFailed`로 바꾼다. 에러 메시지에는 행 id 와 에러 종류만 넣는다 (문의 내용은 넣지 않는다)
- DB 제약(상태 값, New 일 때만 `status_changed_at` null, 칸 길이, slug/연월 형식, 대표 이미지 1개 이하)은 두 번째 방어선이다. 같은 규칙을 DB 에도 적지만 판단의 기준은 domain 이다

## 대안
- 매퍼에서 `createInquiry` 결과에 상태를 펼쳐 덮기: 파일은 하나 줄지만 "도메인 객체는 생성자로만 만든다"는 규칙을 인프라가 우회한다. 저장소가 늘어날 때마다 같은 우회가 복사된다
- 검증 없는 복원(행을 그대로 브랜드 타입으로 캐스팅): 가장 빠르지만 대시보드에서 직접 고친 행이나 마이그레이션 실수가 화면까지 그대로 간다
- 복원 실패 행을 건너뛰고 로그만 남기기: 목록은 계속 보이지만, 관리자 화면에서 문의가 조용히 사라진다. 고장은 드러나는 쪽이 낫다

## 결과
- 저장소 구현이 바뀌어도(Supabase → 다른 DB) 복원 규칙은 그대로다. 매퍼 테스트는 칼럼 변환만 본다
- 읽을 때마다 칸 검증을 다시 돌린다. 문의/작업 수가 수십~수백 개라 비용은 무시할 만하다
- 규칙을 바꾸면(예: 메시지 한도 축소) 이전에 저장된 행이 복원에 실패할 수 있다. 그때는 마이그레이션으로 데이터를 맞추거나 새 ADR 로 복원 규칙을 따로 둔다
