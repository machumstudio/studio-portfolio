# 0014. 작업 사진은 Supabase Storage 공개 버킷에 두고, 브라우저가 서명 업로드 주소로 직접 올린다
- 상태: 채택 (2026-10)

## 배경
18칸에서 관리자가 작업 사진을 올린다. 지금까지 사진은 시드의 로컬 파일(`public/images/works`)뿐이었다.
정할 것은 셋이다: 버킷을 공개로 둘지 비공개 + 서명 URL 로 둘지, 파일을 어떤 길로 올릴지, 작업/사진을 지울 때 파일을 어떻게 지울지.
제약: Supabase 무료 플랜(Storage 1GB, 파일 하나 50MB, 이미지 변환 없음), Vercel 서버 액션 본문 4.5MB, 공개 화면은 `use cache`(시간 단위)로 미리 그린다 (14칸).
관리자 세션 쿠키는 httpOnly 라 브라우저에는 Supabase 클라이언트가 없다 (ADR 0012, 17칸).

## 결정
- **공개 버킷 `work-photos`** (마이그레이션 `20261025000002_work_photos_storage.sql`). 사진 주소는 `/storage/v1/object/public/work-photos/<작업 id>/<UUID>.<확장자>`
  - 목록(list), 올리기, 지우기는 관리자 세션만 (`is_admin()` 정책, ADR 0012). update 정책이 없어 아무도 덮어쓰지 못한다
  - 버킷 한도: 10MB, `image/jpeg`·`image/png`·`image/webp`. `application/works/photo-limits.ts` 와 같은 값이다 (`text/html` 같은 형식은 버킷이 거부한다)
  - 파일 이름은 서버가 정한 UUID. 원본 파일 이름(개인정보가 들어갈 수 있다)은 쓰지 않는다
- **올리기**: 서버 액션은 관리자를 확인하고 서명 업로드 주소(2시간, 그 경로 하나)만 만든다. 브라우저가 그 주소로 직접 PUT 한다 (진행률은 XMLHttpRequest).
  올리기 전에 브라우저가 긴 변 2400 으로 줄이고 다시 인코딩한다 (EXIF 위치 정보가 남지 않고 용량이 1/5~1/10 로 준다)
- **작업 사진의 `src` 에는 공개 주소 전체를 저장**한다. 시드 사진은 지금처럼 `/images/works/...` 다. 저장소 구현(`pathOf`)이 자기 주소만 경로로 되돌리므로
  두 종류가 한 작업 안에 섞여도 되고, 시드 파일은 정리 대상이 아니다. `next.config` 의 `images.remotePatterns` 는 이 버킷 경로만 연다
- **고아 파일 정리**: 작업을 저장하거나 지운 뒤 어느 작업에도 없는 파일을 지운다 (`cleanUpPhotos`). 그 작업 폴더는 바로, 다른 폴더는 하루 지난 것만
  (올리고 저장하지 않고 떠난 새 작업). 정리가 실패해도 저장은 되돌리지 않고 경고로 남기고, 다음 정리가 다시 지운다
- 작업 저장은 Postgres 함수 `save_work` 하나로 작업 행과 사진 행을 한 트랜잭션으로 바꾼다 (PostgREST 요청 여러 개는 중간 실패 때 사진 없는 작업을 남긴다)
- cache-control 은 기본값(1시간). 파일 이름이 바뀌지 않으니 길게 둘 수 있지만, 무료 플랜 CDN 은 지워도 캐시를 비우지 않아 지운 사진이 그만큼 더 보인다

## 대안
- **비공개 버킷 + 서명 URL**: 비공개 작업의 사진까지 주소로 막을 수 있다. 하지만
  - 공개 화면은 몇 시간씩 캐시해서 미리 그리는데 서명 URL 은 만료가 있다. 캐시 수명보다 길게 서명하면 막는 의미가 줄고, 짧게 하면 캐시된 화면의 사진이 깨진다
  - 서명이 바뀔 때마다 next/image 최적화의 캐시 키가 달라져 Vercel 무료 이미지 최적화 한도를 빨리 쓴다
  - 보호 이익은 "공개 전 사진"뿐이다. 공개 작업 사진은 어차피 누구나 본다
- **서버를 거쳐 올리기**(서버 액션에 파일): 코드가 단순하지만 Vercel 본문 4.5MB 에 걸리고, 줄이기 전 원본(위치 정보 포함)이 서버를 지난다
- **Supabase 이미지 변환으로 크기 맞추기**: Pro 플랜 기능이다. 원본을 그대로 저장해 1GB 를 빨리 쓴다
- **사진 경로만 저장하고 주소는 읽을 때 만들기**: 프로젝트 주소가 바뀌어도 데이터가 그대로지만, 시드 사진과 Storage 사진을 구분하는 표시가 하나 더 필요하다.
  프로젝트를 옮길 일이 생기면 그때 마이그레이션으로 주소를 바꾼다

## 결과
- 비공개 작업의 사진도 주소를 알면 열린다. 주소는 추측할 수 없고(UUID) 목록은 관리자만 보지만, 공개했다가 비공개로 돌린 사진의 주소는 이미 퍼졌을 수 있다.
  운영 매뉴얼에 "공개하면 안 되는 사진은 올리지 않는다"를 적는다 (22칸)
- 지운 사진은 CDN 에 최대 1시간 남을 수 있다
- 1GB 안에서 장당 1~3MB 로 수백 장. 장수는 작업당 30장으로 막는다
- Storage 동작(서명 업로드, 형식/크기, 덮어쓰기 금지)과 권한은 계약 테스트가 지킨다 (`photo-storage.contract.ts`, `photo-storage-rls.contract.test.ts`).
  인메모리 구현이 같은 계약을 통과해 e2e 는 클라우드 없이 같은 업로드 경로를 탄다
