# 0012. 관리자 화면은 로그인 세션(authenticated) + RLS `role=admin` 정책으로 테이블을 쓴다
- 상태: 채택 (2026-10)

## 배경
18칸(작업 관리, 사진 업로드)과 19칸(문의 관리)은 관리자만 쓰는 읽기/쓰기다. 지금 서버는 secret 키(service_role, RLS 우회) 클라이언트 하나로 공개 작업 읽기와 문의 저장을 한다.
관리자 쓰기도 같은 secret 키로 할지, 로그인한 관리자의 세션(publishable 키 + 사용자 JWT, `authenticated` 역할)으로 하고 DB 정책이 관리자만 허용하게 할지 정해야 한다.
관리자는 Supabase Auth 의 `app_metadata.role = "admin"` 인 계정이다 (17칸, 공개 가입 꺼짐).

## 결정
- 관리자 화면과 관리자 서버 액션은 **요청의 관리자 세션으로 만든 Supabase 클라이언트**로 테이블과 Storage 를 쓴다. secret 키는 관리자 경로에서 쓰지 않는다
- 권한 확인은 두 번 한다
  1. 서버: 액션/페이지가 데이터에 닿기 전에 `getCurrentAdmin`(인증 서버에서 토큰 확인 + `authorizeAdmin`). 실패하면 로그인으로
  2. DB: RLS 정책 `public.is_admin()` = `auth.jwt() -> 'app_metadata' ->> 'role' = 'admin'` (`supabase/migrations/20261024000003_admin_access.sql`)
- 정책: 작업/사진은 관리자가 전체 읽기·추가·수정·삭제, 문의는 관리자가 읽기·수정·삭제. **새 문의 저장은 지금처럼 secret 키만** (관리자에게 insert 권한 없음). truncate 는 아무 역할에도 주지 않는다
- 판정은 `app_metadata` 만 본다. `user_metadata` 는 사용자가 `updateUser` 로 고칠 수 있다 (RLS 계약 테스트가 user_metadata 를 admin 으로 바꾼 세션이 막히는지 본다)
- 공개 사이트(공개 작업 읽기, 문의 제출)와 시드/계약 테스트는 지금처럼 secret 키를 쓴다
- 18칸 Storage 버킷 정책도 같은 `is_admin()` 을 쓴다. 사진 업로드를 브라우저에서 Storage 로 직접 보낼 수 있어 서버 액션 본문 한도(Vercel 4.5MB)에 걸리지 않는다

## 대안
- **서버에서 세션 확인 후 secret 키**: 코드가 가장 단순하고(14칸 리포지토리 그대로), 정책이 필요 없다. 하지만 액션 하나에서 확인을 빠뜨리면 그대로 전체 권한이 된다. secret 키를 쓰는 코드 경로가 늘어 유출 시 피해 범위가 넓고, 사진 업로드는 서버를 거치거나 서명 URL 을 따로 만들어야 한다
- **DB 에 관리자 목록 테이블**(`admins(user_id)`)을 두고 정책에서 조회: 역할 회수가 즉시 반영되지만 테이블, 정책, 관리 화면이 하나씩 늘어난다. 관리자가 1명인 지금은 과하다

## 결과
- 서버 확인을 빠뜨려도 DB 가 관리자가 아닌 세션을 0행/42501 로 막는다. 대신 정책과 권한(grant)을 마이그레이션에서 관리하고, RLS 계약 테스트(`admin-rls.contract.test.ts`)로 지킨다
- 관리자 리포지토리는 요청마다 세션 클라이언트로 만들어야 한다 (모듈 하나에 클라이언트 하나인 지금의 공개 리포지토리와 다르다). 18칸에서 `container.adminAuth` 옆에 요청 단위 조립을 둔다
- JWT 의 `app_metadata` 는 토큰이 갱신될 때(최대 1시간) 바뀐다. 역할을 회수해도 DB 정책은 그 사이 이전 토큰을 믿는다. 서버 확인(`getUser`)은 바로 반영되므로 화면과 액션은 즉시 막힌다. 급하면 대시보드에서 사용자 세션을 끊는다
- 공개 가입과 익명 로그인이 켜지면 아무나 `authenticated` 세션을 얻는다. 정책이 `role=admin` 을 보므로 권한은 없지만, 계약 테스트가 두 설정이 꺼져 있는지 매번 확인한다
