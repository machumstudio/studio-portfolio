# 0016. 관리자 문의 화면: 필터와 페이지는 주소에, 상태 바꾸기와 지우기는 폼 POST + redirect 로 두고, 상세를 열어도 자동으로 확인하지 않는다
- 상태: 채택 (2026-10)

## 배경
19칸은 비개발자 운영자가 문의를 받고(New) 읽고(Read) 답장을 끝내는(Done) 화면이다. 상태 전이 규칙과 `changeInquiryStatus` 는 12칸에 있다.
정해야 할 것:
- 문의가 쌓였을 때 목록을 어떻게 나눌지. Supabase(PostgREST)는 한 응답의 행 수를 `max-rows`(기본 1000)로 **오류 없이** 자른다
- 상태 버튼의 결과를 어떻게 돌려줄지. ADR 0013: 세션을 읽는 동적 화면에서는 JS 없는 제출 뒤 `useActionState` 결과가 다시 그려지지 않는다
- 같은 문의를 두 탭(또는 PC 와 휴대폰)에서 처리할 때 어떻게 보일지
- 상세를 열면 "확인"으로 바꿀지
- ADR 0015 가 미뤄 둔 질문: 문의 목록에 클라이언트 캐시나 새 문의 자동 갱신이 필요한지

## 결정
- **목록은 저장소에서 범위로 자른다.** `AdminInquiryRepository.findPage({ status, offset, limit })` 는 `received_at desc, id desc` 로 정렬해 20건씩 읽는다
  (같은 시각이 있어도 페이지 사이에서 빠지거나 겹치지 않는다). 개수는 상태마다 `head` + `count=exact` 로 행 없이 센다.
  전부 읽어야 하는 곳(`findAll`, 계약 테스트의 백업)은 빈 응답까지 이어 읽는다(`selectAllPages`). 계약 테스트가 1005건으로 확인한다
- **필터와 페이지는 주소**(`/admin/inquiries?status=new&page=2`)다. 링크라 JS 없이 되고, 뒤로 가기·새로 고침·로그인 뒤 돌아오기에서 그대로다.
  범위를 벗어난 페이지(지운 뒤 사라진 마지막 페이지 등)는 가까운 페이지를 보여 준다
- **상태 바꾸기와 지우기는 숨은 칸(id, action)이 든 폼 POST → 서버 액션 → 결과를 주소의 `notice` 로 redirect** 한다(PRG).
  JS 가 없어도 결과 화면이 보이고, JS 가 있으면 같은 redirect 로 화면만 바뀐다. 성공/충돌/장애 모두 다시 그린 화면이 **지금 상태**와 그때 누를 수 있는 버튼을 보여 준다.
  액션은 `revalidatePath("/admin", "layout")` 로 관리자 화면의 라우터 캐시를 비워 메뉴의 "새 문의 N건"과 필터 개수가 바로 맞는다
- **두 탭 충돌은 도메인 규칙 그대로 처리한다.** 오래된 화면의 버튼은 지금 상태에서 허용되지 않은 전이라 `InvalidTransition` 이 되고,
  "다른 탭이나 기기에서 먼저 바꿨습니다" 알림과 함께 지금 상태를 다시 보여 준다. 지워진 문의는 목록 + "찾을 수 없습니다"
  - 조회 → 전이 → 저장은 한 트랜잭션이 아니다. 하지만 상태마다 허용된 동작이 정확히 하나라, 같은 순간 같은 상태에서 온 두 요청은 같은 동작이고 결과 상태도 같다
    (바뀐 시각만 나중 것이 남는다). 그래서 버전 칼럼이나 조건부 update 를 두지 않는다
- **상세를 열어도 자동으로 "확인"으로 바꾸지 않는다.** 목록에서 잘못 누르거나 미리 훑어본 문의가 "새 문의"에서 사라지면 답장을 놓친다.
  운영자가 직접 "확인으로 바꾸기"를 누르고, 화면에도 "열기만 해서는 상태가 바뀌지 않습니다"를 적는다. GET 이 데이터를 바꾸지 않는 것도 덤이다
- **클라이언트 캐시와 자동 갱신은 두지 않는다** (ADR 0015 의 질문에 대한 답). 읽기는 서버 컴포넌트가 요청마다 하고, 새 문의는 알림 메일(15칸)로 먼저 안다.
  목록은 열거나 상태를 바꿀 때 최신이 된다
- 관리자 세션에는 문의 insert 권한이 없어(ADR 0012) 저장소의 `save` 는 upsert 대신 update → 0행이면 insert 로 한다
- 지우기는 행을 완전히 지운다(개인정보 삭제 요청 대응). 확인 창은 작업 지우기와 같은 네이티브 `<dialog>` 라 JS 가 필요하다
- 개인정보: 탭 제목/방문 기록에 이름을 넣지 않는다("문의 보기"). 서버 로그에는 문의 id 와 에러 종류만 남긴다

## 대안
- **커서(keyset) 페이지**(`received_at, id` 다음부터): 깊은 페이지에서도 빠르고 새 문의가 들어와도 밀리지 않지만, "3 / 12 페이지"와 바로 가기가 어렵다.
  관리자 1명, 문의 수천 건 이하라 offset 으로 충분하다. 느려지면 바꾼다
- **useActionState 로 결과를 화면 상태로 돌려주기**: 페이지 이동 없이 알림을 띄울 수 있지만 JS 없이는 결과가 안 보이고(ADR 0013), 개수와 메뉴를 따로 맞춰야 한다
- **상세를 열면 자동 확인**: 클릭 한 번이 줄지만 위의 실수가 생긴다. 필요하면 "확인하고 열기" 같은 명시적 동작을 더한다
- **낙관적 잠금(버전 칼럼 + 조건부 update)**: 동시 요청을 정확히 거르지만, 위 이유로 결과가 같아 칼럼과 마이그레이션만 는다
- **폴링/실시간 구독으로 새 문의 자동 표시**: 화면을 켜 둔 채 기다리는 운영 방식이 아니고 메일 알림이 있다
- **보관(soft delete)**: 실수로 지운 문의를 되살릴 수 있지만, 삭제 요청을 받은 개인정보가 남는다

## 결과
- 상태 버튼, 필터, 페이지는 JS 없이 된다. 지우기 확인 창만 JS 가 필요하다
- 결과 알림이 주소(`?notice=`)에 남아, 그 화면을 새로 고치면 알림이 다시 보인다. 개인정보는 주소에 들어가지 않는다
- offset 페이지라 보는 사이 새 문의가 들어오면 다음 페이지에서 한 건이 겹쳐 보일 수 있다
- 동적 경로(`/admin/inquiries/[id]`)는 응답을 먼저 보내기 시작해, 없는 문의도 상태 코드는 200 이고 화면만 404 다 (관리자 화면은 검색 제외)
  → 21칸에서 proxy 가 확인해 404 로 돌려준다 (ADR 0019)
